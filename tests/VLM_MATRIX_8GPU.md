# Seven-model, six-dataset evaluation on 4/8 independent GPUs

Run from `LiteSpec/` in the existing `litespec-vlm-runtime` environment. This is
a static replicated-batch benchmark, not a serving deployment or TP=8 engine.
The existing Target and Draft checkpoints are reused; no training is started.

```bash
export DLITE_WORKSPACE="$HOME/LMM/gaohl/project/from_aliyun/LDM/dllm_dflash/dllm_vllm/dlite-vlm"
cd "$DLITE_WORKSPACE/LiteSpec"
git pull --ff-only origin research/qwen35-vlm
export RESULT_DIR="$DLITE_WORKSPACE/runs/vlm_matrix_$(date +%Y%m%d_%H%M%S)"
EVAL_GPUS=0,1,2,3,4,5,6,7 \
BATCH_SIZES="1 16 64" EVAL_SAMPLES=64 EVAL_MAX_NEW_TOKENS=256 \
bash tests/run_vlm_matrix_8gpu.sh
cat "$RESULT_DIR/matrix.md"
```

Four GPUs: set `EVAL_GPUS=0,1,2,3` (or the actual idle GPU indices/UUIDs).
Each physical GPU runs at most one model benchmark process. Cells for a fixed
dataset/batch stay on one GPU and reuse that GPU's measured AR baseline. We use
GPU UUIDs for child visibility and persist the GPU inventory.

a subset with `MODELS="dlite_original dflash_vlm_100k"`.

## Dataset / state controls

- Default `TESTS="text-only charxiv_val flickr30k textvqa hr_bench_4k hr_bench_8k"`.
- Default named-image dataset root is `$HOME/LMM/liyt/datasets/jsonl_datas`;
  override `DATA_DIR`, `IMAGE_ROOT`, and `PROMPT_FIELD` if needed.
- GSM8K `TEXT_DATA` defaults to the existing
  `DeepSpec-main-0708-new/eval_datasets/gsm8k.jsonl` path used previously.
- Exactly 64 independent prompts/dataset are sampled with seed 42 and saved as
  immutable evaluation snapshots under `inputs/`. Reference answers are not fed
  to the model. Every model/mode/batch uses these same snapshots.
- Each prompt is replicated B times, so B=64 means 4096 generated sequences per
  cell, not 64 distinct requests with online continuous batching.
- Default `STATE_MODES="per_token compact_replay full_target_replay"` runs a
  global per-token stage first, then compact replay, then the old HF path.
- Default `PROFILE_DECODE=0` prioritizes rates. Set `PROFILE_DECODE=1` and
  `PROFILE_SAMPLES=16` on a fresh run for separate diagnostic passes. No large
  kernel trace is generated by this queue.
- `IMAGE_MAX_PIXELS`/`IMAGE_MIN_PIXELS` apply equally to AR and every Draft.
  Otherwise preserve the processor's existing image budget.

Prepared image inputs remain on CPU; only the current prompt is transferred
to the device before model timing. This avoids retaining 64 high-resolution
images on every GPU. Image preparation and input transfer are excluded from
model timing. Real batch prefill/decode allocations are included in peak GPU
memory, and high-resolution B=64 may still OOM.

## Failures, progress and resume

Each Draft/mode runs in an isolated process, so CUDA OOM releases its allocations
without terminating the other cells. OOM is reported; the queue never silently
reduces batch or image resolution. If AR itself fails, its dataset/batch cells
are marked blocked, since a meaningful speedup cannot be computed.

```bash
# Continue the SAME result directory with the SAME settings and code.
RESUME=1 bash tests/run_vlm_matrix_8gpu.sh
# Also retry previously recorded OOM cells:
RESUME=1 RETRY_OOM=1 bash tests/run_vlm_matrix_8gpu.sh
```

`RESULT_DIR` must still point to the original run. Repeat all non-default
selectors/overrides when resuming. Completed cells and, by default, OOM cells
are skipped. Failed/interrupted cells get a new attempt directory. Resume
rejects changed data/checkpoints/code/settings/physical GPUs. A file lock
prevents two schedulers writing to the same result directory. Ctrl-C terminates
the queue's child process groups; it never kills unrelated GPU jobs.

`DRY_RUN=1` resolves files/checkpoints and writes the manifest without GPU/model
execution. Run that directory later with `RESUME=1`. A dry run does not prove
weights, kernels or GPU memory will work.

## Outputs

- `matrix.md`: six datasets x three state-mode tables, all seven Drafts and AR,
  columns B=1/16/64; cells show speedup / mean committed length.
- `matrix.csv`: raw throughput, acceptance, GPU, memory, statuses, cross-mode
  token/acceptance equality, and optional profile measurements.
- `ar_baselines.json`: the actual same-GPU AR baselines reused by all modes.
- `manifest.json`, `gpu_inventory.json`, `inputs/`: experiment identity.
- `jobs/<dataset>_b<B>/ar/`: reusable baseline and its logs.
- `jobs/<dataset>_b<B>/<mode>/<model>/`: status, attempt logs, result symlink,
  per-request tokens and optional inference profile report.

Rates never mix profiling time into normal throughput. The two new state modes
share a recurrent verify kernel; old-vs-new also changes verification kernels.
Raw speedup does not imply token-exact agreement with native HF AR. See
`QWEN35_STATE_MODES.md` for state recovery scope and correctness checks.
